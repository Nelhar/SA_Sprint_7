# Модель угроз: границы доверия Fraud Detection Service

**Инициатива:** #1 Выявление подозрительных операций
**Связь:** ai_service_architecture.md (Happy Path), c4_container_fraud_detection.puml

---

## Зачем этот документ

Схема в ai_service_architecture.md показывает, что происходит в обычном случае, куда уходят неоднозначные операции и как сервис переживает отказ модели. Но у системы есть **четыре точки, где она разговаривает не сама с собой**, а пересекает границу доверия: с фронтом банка, с внешним OFAC API, с внешней базой рисков контрагентов и с людьми (очередь экспертов). На каждой такой границе нужно отдельно ответить на три вопроса:

1. **Кто может передать данные** под видом легитимного источника (spoofing / unauthorized access)?
2. **Что может подменить решение** по пути (tampering)?
3. **Чем это закрывается** (mitigation)?

---

## Граница 1: Banking Frontend ↔ API Gateway

Внешний клиент (пользователь банка) инициирует операцию через Banking Frontend, который отправляет её в Fraud Detection через API Gateway (Kong).

### Кто может передать данные

| Угроза | Описание |
|--------|----------|
| Скомпрометированное клиент-приложение | Троян на устройстве клиента или MITM на канале клиент↔банк отправляет операции от имени легитимного пользователя |
| Утёкшие credentials Frontend-сервиса | API-ключ или сервисный токен Frontend украден → атакующий обращается к Gateway напрямую, минуя UI |
| Инсайдер с доступом к Frontend | Сотрудник банка с доступом к продакшен-конфигу Frontend инициирует поддельные операции |

### Что может подменить решение

| Угроза | Описание |
|--------|----------|
| Модификация payload в пути | Без подписи запроса атакующий на промежуточном узле меняет сумму или получателя операции |
| Replay-атака | Ранее перехваченная легитимная операция отправляется повторно |
| Нарушение идемпотентности | Дублирование операции из-за retry без idempotency-key → двойное списание/зачисление |

### Чем закрывается

- **mTLS** между Frontend и Gateway — обе стороны аутентифицируют друг друга, канал зашифрован
- **Request signing (HMAC)** + обязательный **idempotency key** на каждую операцию — повтор с тем же ключом не создаёт вторую операцию
- **JWT с коротким TTL** + refresh-token flow — украденный токен быстро протухает
- **Rate limiting + anomaly detection на Gateway** — внезапный всплеск операций с одного клиента/IP триггерит алерт до попадания в Rules Engine
- **Immutable audit log на входе** (кто, когда, что отправил, с какого IP) — non-repudiation

## Граница 2: Fraud Detection ↔ OFAC Check (внешний API)

Gateway обращается к внешнему сервису проверки чёрного списка (санкционные списки).

### Кто может передать данные

| Угроза | Описание |
|--------|----------|
| DNS spoofing / поддельный endpoint | Запрос уходит не к настоящему OFAC API, а к серверу атакующего |
| Скомпрометированный внешний провайдер | Supply chain risk — сам провайдер OFAC-данных скомпрометирован и отдаёт заведомо неверные ответы |

### Что может подменить решение

| Угроза | Описание |
|--------|----------|
| MITM на канале к OFAC | Подмена ответа "не в списке" на легитимный, хотя контрагент реально в списке → фрод проходит как чистая операция |
| Устаревший локальный кеш | Если чёрный список кешируется локально, staleness — это уже не только security, а операционный риск: контрагента добавили в список вчера, а у нас кеш недельной давности |
| **Fail-open по умолчанию** | Если OFAC API недоступен, наивная реализация "пропускает операцию, раз проверить нечем" — это САМАЯ опасная ошибка на этой границе |

### Чем закрывается

- **TLS + certificate pinning** на канале к OFAC — исключает MITM даже при компрометации DNS
- **Fail-closed / fail-to-expert политика** (а не fail-open!): если OFAC недоступен → операция НЕ авто-одобряется, уходит в expert_queue как Availability Escalation (см. ai_service_architecture.md, раздел "Эскалация по доступности")
- **TTL на локальный кеш ≤ 24 часа** + принудительная сверка для операций выше 500K ₽ (Urgent-класс не должен полагаться на устаревший кеш)
- **Логирование каждого запроса к OFAC** — это одновременно security-контроль и регуляторное требование АМЛ (доказательство, что проверка санкционных списков реально выполнялась для каждой операции)

## Граница 3: Fraud Detection ↔ Counterparty Risk DB (внешняя база рисков)

Gateway/ML Service обращается к внешней базе данных для получения риск-скора контрагента.

### Кто может передать данные

| Угроза | Описание |
|--------|----------|
| Утёкшие credentials сервисного аккаунта | Скомпрометированный API-ключ, читающий Risk DB |
| Data poisoning у внешнего провайдера | Инсайдер риск-провайдера или атака на их систему искажает риск-профили контрагентов |

### Что может подменить решение

| Угроза | Описание |
|--------|----------|
| Подмена risk score в пути | Без подписи ответа — искусственное занижение риска контрагента → ML недооценивает fraud-вероятность |
| Injection через поля ответа | Если Risk DB возвращает свободный текст без санитизации, это потенциальный вектор для downstream-систем (например, в Audit Log UI) |
| Устаревшие риск-данные | Риск-профиль контрагента изменился, но локальный кеш не обновился — эффект эквивалентен tampering, хотя источник другой |

### Чем закрывается

- **Contract Validator** (уже часть архитектуры, см. component_design.md) — отклоняет неожиданный формат/тип данных до того, как они попадут в ML-фичи
- **TLS + ротация API-key** сервисного аккаунта
- **TTL на кеш риск-данных ≤ 24 часа**, принудительное обновление для операций высокого риска (Yellow/Red/Urgent классов)
- **Санитизация всех полей** перед записью в БД/логи — защита от injection в downstream
- **Мониторинг аномалий на уровне признаков** (Feature Drift Detector из monitoring_plan.md уже это частично покрывает): если риск-скор массово и резко падает у большого числа контрагентов одновременно — это либо баг, либо атака на источник, в обоих случаях повод для алерта

## Граница 4: Fraud Detection ↔ Expert Queue (люди — инсайдерская угроза)

Yellow-класс операций уходит на ручную проверку AML-экспертам. Это единственная граница, где угроза исходит не от внешней системы, а от легитимного, аутентифицированного пользователя с правами.

### Кто может передать данные

| Угроза | Описание |
|--------|----------|
| Скомпрометированный аккаунт эксперта | Фишинг/украденные credentials — атакующий действует от имени легитимного эксперта |
| Избыточные права | Эксперт с доступом шире, чем нужно (видит/меняет операции вне своей очереди) |

### Что может подменить решение

| Угроза | Описание | Почему это особенно опасно |
|--------|----------|---|
| **Сговор (collusion)** | Эксперт намеренно подтверждает fraud-операцию как легитимную за откат | Это НЕ баг системы — легитимный workflow используется как прикрытие. Самая серьёзная угроза на этой границе |
| Rubber-stamping | Эксперт подтверждает решения ML не глядя (не обязательно злонамеренно, но по эффекту равнозначно tampering) | Снижает ценность human-in-the-loop до нуля незаметно для метрик Precision/Recall |
| MITM между Expert UI и Dispatcher | Если внутренний трафик не зашифрован — теоретическая возможность подмены решения при передаче | Актуально в первую очередь при недоверенной внутренней сети |

### Чем закрывается

- **Two-person rule для Urgent-класса** (>500K ₽) — уже заложено в Risk-Automation Matrix (Task3/README.md): подпись Head of AML обязательна, один эксперт не может в одиночку закрыть крупную операцию
- **Expert Behavior Monitoring** (уже есть в monitoring_plan.md, Tier 5) — correction rate и post-confirmation error rate вместе статистически ловят и rubber-stamping (метрики "слишком гладкие"), и потенциальный сговор (аномальный паттерн подтверждений у конкретного эксперта)
- **RBAC**: эксперт видит и может решать только операции из своей очереди, не может делать произвольный поиск по всей базе
- **Immutable audit log** (append-only) — эксперт не может задним числом изменить своё решение без видимого следа
- **Ротация распределения операций между экспертами** — усложняет таргетированный сговор ("нужная" операция не гарантированно попадёт к конкретному эксперту)
- **mTLS/шифрование внутреннего трафика** Expert UI ↔ Dispatcher — закрывает теоретический MITM даже во внутренней сети

## Сводная таблица (для быстрого просмотра)

| Граница | Главная угроза | Ключевая мера |
|---------|----------------|---------------|
| Frontend ↔ Gateway | Подмена/replay операции | mTLS + HMAC-подпись + idempotency key |
| Gateway ↔ OFAC | **Fail-open при недоступности** | Fail-closed → expert_queue, а не auto-allow |
| Gateway/ML ↔ Risk DB | Устаревшие/подменённые риск-данные | Contract Validator + TTL кеша ≤24ч |
| Dispatcher ↔ Expert Queue | **Сговор эксперта (collusion)** | Two-person rule + Expert Behavior Monitoring |

Две угрозы отмечены как приоритетные: **fail-open на OFAC** (потому что тихо превращает security-контроль в decorative) и **сговор эксперта** (потому что использует легитимный workflow как маскировку и не ловится обычными ML-метриками — только поведенческим мониторингом).
